Client Portal · Database design · Proposed v1

What the portal stores, and how it stays in step with Zoho CRM

The portal runs on Zoho Catalyst with a Supabase PostgreSQL database. Zoho CRM remains the master record for every client, deal, listing and lead. The database keeps the portal's own data plus a synced copy of the Zoho records it shows, so pages load fast without hammering the Zoho API.

How data moves

Clients only ever talk to the portal. Every change is written to Zoho first; Zoho then tells the portal what changed.

Fast pages

Database reads, not API calls

A dashboard is one indexed query on the copy, instead of several Zoho API calls (contact, related deals, each deal's agent) per page view.

Zoho stays in charge

Write to Zoho, then copy

The portal never edits its copy on its own. If a Zoho write fails, nothing changes and the client is asked to retry.

Fresh within seconds

Webhook + 10-minute catch-up

Each copied row keeps Zoho's record id and Modified_Time, so the sync only fetches what changed since its last run.

Within Zoho's API limits

Calls scale with changes, not visits

Zoho CRM limits API calls per day. Reading from the copy means 1,000 clients refreshing their dashboard costs no extra Zoho calls.

What is stored where

Only what the portal shows is copied. Internal agent notes and everything else in Zoho stay in Zoho.

DataMaster recordIn the portal databaseWhy
Clients, agents, deals, pipeline stagesZoho CRMSynced copyMy Deals, deal status and AI insights load instantly

Activity logPortalPortal-ownedTamper-evident audit trail, admins only

Where we are

Built and tested

  • All 13 tables, keys and rules, in a private portal schema
  • Schema applied and the full test suite passing on PostgreSQL 16 (Supabase runs PostgreSQL)
  • Supabase lockdown: no access through Supabase's public Data API
  • Portal-owned tables in use: logins, consents, sign-in codes, audit trail
